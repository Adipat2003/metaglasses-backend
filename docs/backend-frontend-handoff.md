## Architecture and responsibilities

- The phone owns its Talk transcript, voice capture, speech recognition, and speech synthesis.
  Guide drafts from a goal, requires user approval of the exact version, then pins it in a run.
- RDS stores owner-scoped runs and serializes transitions per owner. PostgreSQL enforces one
  active run and keeps paused runs available across sessions. Only user commands advance a step.
- The API uses owner-checked PostgreSQL functions and private S3 objects for images. Migration
  functions expose narrow execute permissions to `metaglasses_api`. AWS IAM and the private
  network control service access. Bedrock reviews plans and camera frames. Managed Talk uses NVIDIA.
- Goal drafting, versioned approval, and phone chat use a six-minute request lease and a 24-hour
  replay record with a digest and bounded result. Cleanup removes expired records and images.
  Camera workers claim with a 30-second lease, reject stale state, and allow at most two claims.
  See [AWS operations](aws-deployment.md).
- Legacy lens pairing uses a secure random 16-byte capability encoded as 32 hexadecimal
  characters. Protect it in transfer, local storage, and logs. The lens polls the shared display.
  A phone-only flow can proceed with the access token alone.

## Shared HTTP conventions

Append paths below to the confirmed base URL, without a trailing slash. Protected requests use `Authorization: Bearer <COGNITO_ACCESS_TOKEN>`. JSON requests use `Content-Type: application/json`; image upload uses raw binary bytes. UUIDs are RFC-compatible strings. Each response has `x-request-id`; record that ID with a safe error report. The API currently responds to CORS preflight and allows any origin, but CORS is not authorization. `204` responses have no JSON body. Always check HTTP status before parsing a response.

Errors generated by the backend API have this shape (fields in `context` are optional). API Gateway, infrastructure, and network failures can have a different format or no response, so clients must also handle non-JSON failures:

```json
{
  "detail": "Task run state changed. Refresh and retry.",
  "request_id": "<REQUEST_UUID>",
  "status": 409,
  "error": {
    "type": "ApiError",
    "code": "task_run_stale",
    "message": "Task run state changed. Refresh and retry.",
    "context": { "state_version": 2 }
  }
}
```

Use `error.code` for program logic and `detail` or `error.message` for a safe user-facing message. `error.context.suggested_action` is present on some errors. Handle `401` by renewing the user session or re-pairing as appropriate; `403` means a pairing belongs to another user; `404` can mean an unavailable resource or expired pairing; `409` requires resolving a state or plan conflict; `413`, `415`, and `422` require correcting input; `429` requires respecting limits; `503` indicates a dependency failure. Never automatically retry a non-idempotent operation with a new ID after an uncertain outcome. Health success alone does not check model, database, or storage readiness.

Example reusable request helper:

```js
async function api(path, { accessToken, ...options } = {}) {
  const headers = new Headers(options.headers);
  if (accessToken) headers.set("Authorization", `Bearer ${accessToken}`);
  const response = await fetch(`${API_BASE}${path}`, { ...options, headers });
  if (!response.ok) {
    const body = await response.json().catch(() => null);
    throw { status: response.status, requestId: response.headers.get("x-request-id"), body };
  }
  return response.status === 204 ? null : response.json();
}
```

`API_BASE` and the current access token must be supplied by the app. A thrown network error is not
an API error envelope, so handle it separately and retain the logical request ID before retrying. Encode query parameters with `URLSearchParams`. The helper intentionally leaves retries and session refresh to the application.

## Pairing and display

### Health

`GET /healthz` returns `{"status":"ok","environment":"aws","auth":"required"}` in an AWS-configured process. `environment` depends on runtime configuration.

### Register and maintain a pairing

`POST /v1/state` requires a user token:

```json
{"pairingToken":"<32_HEX_CHARACTERS>","state":"listening"}
```

Valid states are `idle`, `listening`, `thinking`, and `speaking`. The token is exactly 32 hexadecimal characters. A successful request returns 204. Pairing lifetime is 3,600 seconds from phone activity; refresh it while the session is in use. The database stores a hash of the pairing capability and associates it with the authenticated owner. Another user cannot use an active pairing through protected routes. Once expired, a pairing needs registration again. Do not assume lens polling extends its lifetime.

### Read the lens display

`GET /v1/display?token=<PAIRING_TOKEN>` requires the pairing capability, not the phone's bearer token:

```json
{"responseId":"r_<ID>","text":"Hello","state":"speaking","createdAt":"2026-01-01T00:00:00.000Z"}
```

Before a response is published, `responseId`, `text`, and `createdAt` can be null. Poll at a product-chosen bounded cadence and render updates when `responseId` changes; no server push or mandated polling interval is implemented. The latest display is shared by chat and task guidance. `401` for an unknown or expired token means the phone should re-pair. No endpoint returns historical display messages.

## Images and chat

### Upload and delete

Upload raw JPEG or PNG bytes with a matching `Content-Type` to `POST /v1/images`. Omit scope
parameters for a private Talk image (8 MiB maximum). Send `taskRunId` for the caller's active run
(2 MiB maximum), or `pairingToken` for legacy paired media (8 MiB maximum). Use a stable
`clientImageId` to retry the same bytes in the same scope. The 201 response supplies
`imageId`, `contentType`, `byteSize`, and `createdAt`. Use the same scope with
`DELETE /v1/images/<IMAGE_UUID>`. Images are temporary and subject to cleanup.

### Chat

`POST /v1/chat` accepts phone Talk with a stable request ID and the relevant local transcript.

```json
{
  "clientRequestId":"<UUID>",
  "messages":[{"role":"user","content":"What tool should I use next?"}],
  "taskRunId":"<TASK_RUN_UUID>",
  "expectedStateVersion":1
}
```

Run ID and version are optional together. Add `observationWindowId` to reuse an observed window
for the same run and version, with its newest frame captured within 10 seconds. An old
observation returns `409 observation_stale`. Use owner-only Talk images on user messages and
keep normalized messages within 256,000 UTF-8 bytes. The response includes `responseId`, `text`,
`createdAt`, and, for run-context calls, `taskRunId` and `stateVersion`. Retry phone chat with the
original payload and ID. The legacy body uses `pairingToken` and publishes to the lens.

### Optional user-supplied provider

A request may include `provider`, for example `{"type":"openai","apiKey":"<USER_API_KEY>","model":"<MODEL>"}`. Supported types are `openai`, `anthropic`, `google`, `azure`, `aws-bedrock`, `nvidia`, `openrouter`, `groq`, `mistral`, `xai`, `together`, `fireworks`, `deepseek`, `perplexity`, and `cerebras`. Azure also requires `endpoint`; Bedrock uses `region`, `accessKeyId`, `secretAccessKey`, optional `sessionToken`, and `model`. See [provider examples](../README.md#use-your-own-model-provider) and [`providers.ts`](../backend/api/providers.ts) for validation and model-specific behavior. Credentials are supplied for that request and are not intended to be stored by the backend. A failed user-provider request does not fall back to the managed provider. A frontend offering this feature must protect credentials in transit and on device, and never log them.

## Task plans: create, review, refine, approve

Plans are separate from device pairings. Any signed-in user can discover, read, and use approved plans. Drafts and plans awaiting approval are visible only to their creator. Approval makes the plan's title, steps, and review available to all signed-in users; the creator's revision history is private. Keep the returned IDs and versions. UUID request IDs identify a logical operation: reuse the same ID and same payload for a retry after an uncertain result, and generate a new ID for a new operation. Do not change payloads under a reused ID.

Unapproved plans expire **two hours after `createdAt`**, including time spent refining them. Editing does not extend the deadline. Show the returned `expiresAt` and warn the user before it arrives. Once expired, an unapproved plan is unavailable even if background cleanup has not yet removed its database row. Cleanup runs in batches while the AWS API process is running; approved plans have `expiresAt: null` and are not deleted by this cleanup. `410 task_plan_expired` can occur when retrying a recently expired creation; create a new plan with a new request ID. Once the old row is deleted, the server no longer retains that request ID, so do not retry it as an old operation.

### Browse and select plans

Send `GET /v1/task-plans?status=approved&limit=50&offset=0` with the Cognito access token to browse all shared approved plans. Omit `status` to include the user's own unexpired drafts and awaiting-approval plans alongside shared approved plans. Supported statuses are `draft`, `awaiting_approval`, `approved`, and `abandoned`. A status filter never exposes another user's unapproved plan. The default page size is 50, the maximum is 100, and `offset` defaults to 0. Invalid, repeated, or unknown query parameters return 422.

```json
{
  "items": [{
    "taskPlanId":"11111111-1111-4111-8111-111111111111",
    "title":"Place a cup on a table",
    "status":"approved",
    "isOwner":false,
    "currentVersion":2,
    "approvedVersion":2,
    "createdAt":"2026-01-01T12:00:00.000Z",
    "updatedAt":"2026-01-01T12:05:00.000Z",
    "expiresAt":null
  }],
  "nextOffset":null
}
```

`isOwner` lets the app identify the user's own plans without exposing another user's identity. If `nextOffset` is a number, request the next page with the same status and limit and that offset. Results are ordered by creation time descending, then plan ID descending. Because this is offset pagination, new or newly approved plans can shift later pages; refresh from offset 0 and deduplicate by `taskPlanId`. To select an item, call `GET /v1/task-plans/<TASK_PLAN_UUID>` for its full steps, review it, and start a phone run with the selected `approvedVersion` as `expectedPlanVersion`. Do not send a start request for an unapproved plan.

### Create

`POST /v1/task-plans`:

```json
{
  "clientRequestId":"<UUID>",
  "title":"Place a cup on a table",
  "steps":[{"instruction":"Place the cup on the table."}]
}
```

The title is 1-160 characters after normalization; there must be 1-30 steps, each instruction 1-1,000 characters, with at most 16,000 combined instruction characters. Text is Unicode NFKC normalized, trimmed, and whitespace collapsed. Pairing is not needed to create a plan. For backward compatibility, an optional `pairingToken` is accepted; if supplied it must be active and owned by the caller. Omit it in new clients. For phone goal drafting, send `{"clientRequestId":"<UUID>","goal":"Make a paper bookmark"}` instead of this structured form. A goal may contain up to 2,000 characters after normalization. The response is a 201 with a reviewable draft. Structured creation saves the original steps as version 1 and uses the model to produce a draft proposal as version 2. Success is 201 and returns the current plan. Retry a failed creation with the same clientRequestId and identical request. Its fields include `taskPlanId`, `title`, `status`, `currentVersion`, nullable `approvedVersion`, `createdAt`, `updatedAt`, `sourceSteps` with ordinal and instruction, `validationStatus`, nullable `validation`, and `revisionHistory`. Store the returned `taskPlanId`.

Generated and refined `sourceSteps` also include `prechecks`, `postchecks`, `acceptanceCriteria`, `safetyNotes`, `openQuestions`, and `optionalQuestions`, each an array of up to three strings of at most 240 characters. `instruction` is the action. Render the checks and criteria under their step. Before review, treat `openQuestions` as needing review. A review can explicitly classify the same question as optional; otherwise it blocks approval. Step `optionalQuestions` are nonblocking unless the review separately identifies a safety issue or blocker. Checks are suggestions, not assertions that they passed. Older saved plans and the original version 1 can omit these fields, so treat missing arrays as empty. This is additive: existing clients that render only `instruction` remain compatible, but will not show the detailed guidance until updated.

For example, a step might be `{"ordinal":1,"instruction":"Add banana to the blender.","prechecks":["Check that the blender is ready to use."],"postchecks":["Check that the banana is in the blender."],"acceptanceCriteria":["Banana is visible in the blender."],"safetyNotes":[],"openQuestions":[],"optionalQuestions":["Would you like to slice the banana first?"]}`. The model's actual output can differ; it must not be treated as a completed check.

Offer **I don't know** and **Decide later** for an optional question. The app can keep that choice locally and let the user approve without answering; no special approval parameter is required. The question remains visible in the returned plan and can be shown during the relevant step, but the backend does not schedule a reminder or store the user's per-question choice. After review, match `sourceSteps[].openQuestions` against `validation.optionalQuestions` case-insensitively to show reclassified questions as optional; `clarificationQuestions` and `approvalBlockers` take precedence. If the user wants to answer or believes a required question is optional, submit a refinement message such as “I don't know which milk; leave the type undecided if it is not required.” Review the new version before approval. Selecting an optional-question action does not override a required question or safety blocker. Classification is model-generated and can be wrong; the user must review the plan.

A representative successful creation response follows. IDs and timestamps are examples; generated
text varies. `revisionHistory` contains the model's initial proposal summary, and `sourceSteps`
contains the **current generated proposal**. Initial generation preserves the normalized submitted
instructions and their order; later refinements may change them. Keep a copy of the submitted steps
in the app if the UI must display them later. The current read endpoint does not expose the original
version separately.

```json
{
  "taskPlanId":"11111111-1111-4111-8111-111111111111",
  "title":"Place a cup on a table",
  "status":"draft",
  "currentVersion":2,
  "approvedVersion":null,
  "createdAt":"2026-01-01T12:00:00.000Z",
  "updatedAt":"2026-01-01T12:00:01.000Z",
  "expiresAt":"2026-01-01T14:00:00.000Z",
  "sourceSteps":[{"ordinal":1,"instruction":"Place the cup on the table.","prechecks":["Check that the table surface is clear."],"postchecks":["Check that the cup is on the table."],"acceptanceCriteria":["The cup rests upright on the table."],"safetyNotes":[],"openQuestions":[],"optionalQuestions":[]}],
  "validationStatus":"not_validated",
  "validation":null,
  "revisionHistory":[{
    "clientRequestId":"22222222-2222-4222-8222-222222222222",
    "request":"Organize the supplied steps into a clear task plan while preserving their intent and order.",
    "summary":"Organized the supplied step.",
    "version":2
  }]
}
```

If model generation fails, a draft may already exist even though the app received `503`. Retry
with the identical payload and request ID; do not generate a new ID. Concurrent retries can invoke
the model more than once, but the backend persists one proposal. A reused ID with a different title,
pairing, or steps returns `409 task_plan_idempotency_conflict`. The model runs at temperature zero,
but separate attempts are not guaranteed to produce identical text.

### Read and validate

`GET /v1/task-plans/<TASK_PLAN_UUID>` returns the current representation to its owner, or to any signed-in user if it is approved. Other users receive an empty `revisionHistory`. No pairing is needed. `POST /v1/task-plans/<TASK_PLAN_UUID>/validate` invokes the optional model review for the owner's draft and returns the updated plan. Use `{}` as the JSON body. The validation can report `planSummary`, `needsUserClarification`, required `clarificationQuestions`, nonblocking `optionalQuestions`, normalized `steps`, `planRisks`, `unsupportedClaims`, `guidelineChecks`, `approvalBlockers`, and `approvalReady`. Older saved reviews can omit `optionalQuestions`. Show each step's canonical instruction, visual criteria, risk, and confirmation label as well as the source steps. Validation is not approval.

**Review limitations:** A structurally valid model response can still contain incorrect or contradictory checks. Live tests produced checks that assumed later actions had already occurred, and a review incorrectly marked such a plan ready. `approvalReady` and a successful approval are not guarantees of correctness or safety. Show the full plan for human review, including the sequence, questions, warnings, and checks; let the user refine incorrect details before approval. An explicit approval action remains required. Do not display a failed validation as a successful validation: keep the plan visible, show the error and request ID, and clear any stale success message for that operation.

The backend treats inconsistent clarification fields conservatively. If a review appends extra steps, it omits them and blocks approval with a request to review missing actions. A review with missing or reordered source steps fails safely. Model calls can fail or time out, including during first-time structured-output schema compilation. Use the existing 503 error code and request ID for support; retry without inventing a successful review. The initial AWS model request has a 20-second timeout. Reviews with questions or blockers make a separate classification call with a seven-second timeout; the full request can approach the API Gateway timeout. Only the first 30 distinct items are classified, and later items remain required.

### Refine

`POST /v1/task-plans/<TASK_PLAN_UUID>/refine`:

```json
{"clientRequestId":"<NEW_UUID>","expectedVersion":2,"message":"Make the second step more specific."}
```

The example assumes `currentVersion` is 2, as in a newly generated plan. In an actual request,
always use the latest value returned by create, read, or refine.

The message is 1-2,000 characters after normalization. The response is the updated plan with a new `currentVersion`, cleared review, and revision history. Each new edit needs the latest version and a new request ID. The initial model proposal uses one revision, leaving at most nine refinements. Refinements cannot change the title; they are unavailable after approval or once a run exists. On a version conflict, fetch the plan and let the user review the new state before issuing a new edit. Refinement is a model proposal, so present it for review.

### Approve

After the user explicitly approves the displayed current version, call `POST /v1/task-plans/<TASK_PLAN_UUID>/approve` with `{"expectedVersion":2,"clientRequestId":"<UUID>"}`. The server performs a strict review of that version and atomically checks it has not changed. Legacy clients may send `{}` to review the current version. Calling validate first is optional. On success, the returned plan has `status: "approved"` and an approved version. A `409 task_plan_guidelines_failed` leaves it editable: fetch the plan, show saved blockers and clarification questions, refine, and ask the user to approve again. Other conflicts include stale plan and non-approvable state. Approval is not a model-only action; do not invoke it without a deliberate user action. See [approval guidelines](task-plan-approval-guidelines.md).

## Task runs and visual guidance

### Start and read

Start a phone run with the exact approved version.

```json
{"taskPlanId":"<TASK_PLAN_UUID>","clientRequestId":"<UUID>","expectedPlanVersion":2}
```

The 201 response includes the IDs, `planVersion`, `status`, `currentStepOrdinal`,
`currentStepStatus`, `stateVersion`, `latestSequenceNumber`, `lensInstruction`, and timestamps.
Restore active and paused runs with `GET /v1/task-runs?status=unfinished` and inspect one with
`GET /v1/task-runs/<TASK_RUN_UUID>`. To switch, include
`activeRun: {"taskRunId":"<ACTIVE_UUID>","expectedStateVersion":1}` in the start or resume
request to pause that active run atomically. Reload unfinished runs after an active-run conflict.

Legacy paired starts supply the caller's active `pairingToken` and publish to the lens.
A legacy start without a plan version or pairing uses the original owned active pairing when
available. Retry a start using the exact original payload and request ID.

### Commands and concurrency

`POST /v1/task-runs/<TASK_RUN_UUID>/commands`:

```json
{"clientRequestId":"<UUID>","expectedStateVersion":1,"command":"confirm"}
```

Commands are `pause`, `resume`, `repeat`, `confirm`, `skip`, `back`, `correct`, and `stop`. The server checks the current state, applies the command, increments `stateVersion`, and returns `outcome`, run state, and lens instruction. Pause requires active; resume requires paused; back requires active and a step after the first; confirm and skip require active and advance or complete the final step. Repeat and correct republish the current instruction. Stop ends the run. `POST /v1/task-runs/<TASK_RUN_UUID>/stop` accepts the same body without `command` and forces stop. The server caps recorded commands per run at 1,000.

A successful command response has this shape:

```json
{
  "outcome":"applied",
  "taskRunId":"33333333-3333-4333-8333-333333333333",
  "status":"paused",
  "currentStepOrdinal":1,
  "currentStepStatus":"in_progress",
  "stateVersion":2,
  "lensInstruction":"Guidance paused."
}
```

Use the latest returned `stateVersion` for every command. On `409 task_run_stale`, fetch the run, update the UI, and ask the user to retry an action that is still appropriate. Do not silently replay a stale confirmation. Reuse the original `clientRequestId` and payload only when retrying the same operation after an uncertain network result. User commands, not visual model observations, control step progression.

### Run state and visual step checks

Approval stores a particular plan version. Starting it creates a separate run at step 1, in `active` state with `stateVersion: 1`. `pause` changes active to paused; `resume` changes paused to active. While active, `confirm` or `skip` moves to the next step, or marks the run `completed` on the last step. `back` returns to the previous step when active and not on step 1. `repeat` and `correct` republish the current instruction; `stop` ends an active or paused run. Every accepted command increments `stateVersion`, including repeat and correct. Completed and stopped runs are terminal. The server rejects invalid transitions and stale state versions.

An inference window is an asynchronous observation, not a video stream. The worker sends the current step's instruction, its approved review's `visualAcceptanceCriteria`, and the submitted images to the vision model. The model returns a summary, frame indexes, confidence, and one proposed result: `remain_in_progress`, `candidate_complete`, or `blocked`. The backend validates that response and stores it, but it does **not** change the run's step, status, or `stateVersion`. If the run state changed while inference was in flight, the stale result cannot update the display. A successful current observation publishes the current instruction, a request to confirm possible completion, or a camera-correction prompt to the shared display. The phone can recognize a published result by `responseId: "task_observation_<inferenceWindowId>"`.

Read the result through the camera window endpoint. Ask the user to confirm completion.
Observations describe visible evidence and can be wrong.

### Talking during guidance

Submit recognized speech as Talk text with the current run and version for an explanation about
the step. For a camera question, submit the question and fresh frames together in one window.
A spoken command goes through the same concurrency checks as a tapped command.

### Submit an inference window

Upload 1-3 distinct run-scoped JPEG or PNG frames, up to 2 MiB each. Capture times must be
strictly increasing canonical UTC timestamps with milliseconds. For a new window, the server
accepts captures from 30 seconds before to 5 seconds after server time.

`POST /v1/task-runs/<TASK_RUN_UUID>/inference-windows`:

```json
{
  "clientRequestId":"<UUID>",
  "sequenceNumber":1,
  "expectedStateVersion":1,
  "frames":[{"imageId":"<IMAGE_UUID>","capturedAt":"2026-11-10T12:00:00.000Z"}]
}
```

Use the run's `latestSequenceNumber + 1` and the state version at capture. Include an optional
`question` of up to 500 characters. A 202 returns the window ID and its status. Retain the original
payload for retries, including capture times. Phone runs accept one pending window at a time.

Poll `GET /v1/task-runs/<TASK_RUN_UUID>/inference-windows/<WINDOW_UUID>` until `observed` or
`rejected`, with a client-side deadline. Terminal results include an `observation` or safe
`errorCode` respectively. Compare the
observed state version with current state before showing evidence. Stop capturing when the user
pauses or leaves Guide.

## Error handling by operation

The HTTP status and `error.code` are the contract. The `detail` and `error.message` fields are
user-facing descriptions and can change. `error.context` is optional. The server returns
`x-request-id` on application responses; include it in a support report without logging tokens,
pairing capabilities, request bodies, images, or provider credentials.

| Condition or code | Meaning and frontend action |
| --- | --- |
| `401 unauthorized` or `auth_rejected` | User token is missing, expired, invalid, or issued to a client the backend does not accept. Refresh or sign in; if a fresh access token fails, give support the request ID. |
| `401 unauthorized` on pairing-dependent work or display | The message can instead indicate an unknown or expired pairing. Re-register or re-pair as appropriate. |
| `403 forbidden` | The active pairing belongs to another user. Do not reuse another user's token. |
| `404 not_found`, `task_plan_not_found`, `task_run_not_found` | The resource or active pairing is unavailable to this user. Refresh app state and re-pair if needed. |
| `422 validation_error`, `task_plan_invalid` | Correct the input; do not automatically retry unchanged input. |
| `413 payload_too_large`, `415 unsupported_media_type` | Reduce the transcript or image, or supply a supported JPEG/PNG. |
| `409 task_plan_idempotency_conflict` | A create or refinement request ID was reused for a different operation. Generate a new UUID for the new operation. |
| `409 task_plan_stale`, `task_plan_changed` | Fetch the current plan and let the user review it before issuing a new edit or approval. |
| `409 task_plan_guidelines_failed` | Fetch the plan; show `validation.approvalBlockers` and `clarificationQuestions`, then allow refinement. |
| `409 task_run_idempotency_conflict`, `task_run_already_active` | Use a new request ID for a different run; resume or stop the existing active run before starting that plan version again. |
| `410 task_plan_expired` | The unapproved draft passed its two-hour lifetime. Create a new plan with a new request ID. |
| `409 task_plan_not_draft`, `task_plan_not_refinable`, `task_plan_not_approvable`, `task_plan_has_runs`, `task_plan_revision_limit` | The requested plan operation is unavailable in its current lifecycle. Fetch and display the current state. |
| `409 task_run_not_ready`, `task_run_invalid_transition`, `task_run_not_active` | Check plan approval, pairing, and current run state; do not blindly replay a command. |
| `409 task_run_active_conflict`, `task_run_plan_stale` | Reload unfinished runs or the approved plan before asking for a fresh decision. |
| `409 request_in_progress` | Retry the original payload after allowing the current attempt to finish. |
| `409 window_in_flight`, `observation_stale` | Poll the existing window or capture fresh evidence for a new request. |
| `409 task_run_stale` | Read the run; the optional `error.context.state_version` may help, but use the full current state for the UI. |
| `409 window_out_of_order`, `422 window_media_invalid` | Use the current run's sequence and valid, recent images from its scope. |
| `429 rate_limited`, `model_rate_limited`, `provider_rate_limited`, `task_run_command_limit` | Model rate limits may be transient; the command limit is a per-run cap and waiting alone does not reset it. |
| `503 plan_creation_unavailable`, `plan_creation_invalid_response` | Keep the same create payload and UUID for retry. A draft may already have been saved. |
| `503 plan_refinement_unavailable`, `plan_refinement_invalid_response` | Show the error; retry the same intended revision with its original UUID and payload when appropriate. |
| `503 plan_validation_unavailable`, `plan_validation_invalid_response`, `plan_approval_review_unavailable`, `plan_approval_review_invalid_response` | The model review did not complete or could not be used. Keep the current plan visible and retry when appropriate. |
| `503 pairing_rpc_failed`, `storage_upload_failed`, `storage_delete_failed`, `storage_sign_failed`, `model_request_failed`, `model_provider_error`, `model_invalid_response` | A backend dependency failed. Show safe detail and suggested action when supplied; retain the request ID. |
| `500 internal_error` or another `5xx` | Show a generic recovery message and send the request ID to support. Do not display raw infrastructure responses. |

Transport errors and API Gateway errors may lack the JSON envelope or `x-request-id`. Preserve the
user's unsent input and distinguish a connection failure from a verified backend rejection. Use
bounded, deliberate retries: never automatically retry validation, authorization, or other
non-transient failures. Do not silently retry a user confirmation after a state conflict.

## Suggested frontend sequence

1. Sign in with the target Cognito configuration and restore unfinished runs.
2. Send a goal. Show the resulting steps and questions, refine if needed, then approve the exact reviewed version.
3. Start or resume Guide. Keep the latest step and state version. Keep each logical command's request ID for retries.
4. Ask Talk about a step or capture a bounded camera check.
5. On stale state, read the run and request a fresh user decision. Stop the run and capture when the user is finished.
