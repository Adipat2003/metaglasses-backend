Executive summary

The MetaGlasses backend is a functional v0.1 FastAPI service for a phone-to-lens text-assistance loop. It accepts a phone-maintained conversation transcript, asks OpenAI for one concise next step, and exposes the newest answer to a paired lens. Supabase is used strictly as the identity provider. Pairing and display state remain process-local.

1. System purpose and architecture

The service supports a deliberately narrow interaction model. A phone owns conversation history and voice interaction, while the lens receives only short text and a simple activity state. The backend is the trust boundary between authenticated phone traffic, the OpenAI model provider, and unauthenticated lens polling.

Explicit scope boundaries

  • The backend does not accept, store, or return audio.
  • The backend does not retain the conversation transcript.
  • The backend does not expose login, signup, or refresh-token endpoints.
  • The backend does not use Supabase Postgres, Storage, Realtime, or service-role credentials.
  • The backend does not currently integrate NVIDIA APIs or the previously supplied NVIDIA example.
  • The backend returns one complete text response rather than streaming partial output.

2. API contract and request lifecycle

Endpoint summary

Method and pathAuthenticationPurposeMain responses
GET /healthzNoneReports process status, selected environment, and auth mode200
POST /v1/stateSupabase bearer token outside local modeRegisters a pairing or changes lens state204, 401, 403, 422
POST /v1/chatSupabase bearer token outside local modeGenerates and caches the next display instruction200, 401, 403, 413, 422, 429, 503
GET /v1/display?token=...Pairing-token capabilityReturns newest text and current state to the lens200, 401, 422

Interactive Swagger documentation

Swagger UI is available at /docs, ReDoc is available at /redoc, and the machine-readable OpenAPI document is available at /openapi.json. All four endpoints appear in the schema.

  • System contains process health and runtime-mode visibility.
  • Phone contains authenticated chat and state operations.
  • Lens contains capability-protected display polling.
  • Every operation has a stable operation ID, summary, detailed description, and response description.
  • Request and response fields include human-readable descriptions and representative examples.
  • Application-level 401, 403, 413, 429, and 503 responses are documented with a shared error schema.
  • The authorization dialog identifies the credential as a Supabase bearer access token.
  • Filtering, alphabetical tag sorting, method sorting, request duration, and authorization persistence are enabled.

Input validation

  • A pairing token must contain exactly 32 hexadecimal characters, providing 128 bits when generated randomly.
  • A chat request must contain at least one message.
  • Message roles are limited to user and assistant.
  • Message text cannot be empty or whitespace-only.
  • The serialized transcript cannot exceed 256,000 UTF-8 bytes.
  • State must be idle, listening, thinking, or speaking.
  • External JSON uses camelCase while Python uses snake_case.

Chat sequence

  1. FastAPI and Pydantic validate the bearer header, pairing token, messages, and transcript size.
  2. The store registers or verifies pairing ownership and changes the state to thinking.
  3. The chat service submits the entire supplied transcript and fixed system instruction to OpenAI.
  4. A provider rate limit becomes HTTP 429. A missing key, API error, or empty model output becomes HTTP 503.
  5. On provider failure, the state returns to idle.
  6. On success, a new response ID and UTC timestamp are created, the state becomes speaking, and the newest text is saved.
  7. The API returns that response to the phone. The lens receives the same value on its next poll.

Representative payloads

POST /v1/chat
Authorization: Bearer <supabase-access-token>
Content-Type: application/json

{
  "pairingToken": "a3f9d1e2c3b4a5f60718293a4b5c6d7e",

Capability endpoint /v1/display is intentionally not protected by Supabase. Knowledge of the random pairing token grants read access to its latest display state. Because the token is a URL query parameter, infrastructure logs and browser history must be treated carefully.

3. Supabase authentication

Delivered behavior

The mobile client is expected to authenticate directly with Supabase. It sends the current access token to protected FastAPI routes. The backend uses the configured Supabase URL to retrieve public signing keys and verifies tokens locally. The official Supabase JWT guide documents the project JWKS endpoint and recommends established JWT libraries for verification.

JWT controlCurrent enforcement
SignatureES256 or RS256 only
Issuer{SUPABASE_URL}/auth/v1
Audienceauthenticated by default, configurable
Required claimsexp, iat, and sub
RoleMust equal authenticated
User identityJWT subject, with optional email claim
Key cachingPublic JWKS cached for 600 seconds
Unauthorized response401 with WWW-Authenticate: Bearer

Security choices already made

  • No user password enters FastAPI.
  • No secret or service-role Supabase key is needed by FastAPI.
  • Legacy shared-secret HS256 tokens are deliberately rejected.
  • Authentication bypass is allowed only with APP_ENV=local.
  • Trial and production require HTTPS Supabase URLs.
  • The first authenticated user to register a pairing token owns it until expiration.
  • User-editable metadata is not used for authorization decisions.

Email signup and refresh-token rotation are enabled locally. Email confirmation is disabled locally, anonymous sign-in is disabled, JWT lifetime is one hour, and the native callback is glance-dev://auth/callback. Each developer generates an ignored ES256 signing-key file.

Not yet completed

  • The trial and production project references remain placeholders.
  • Hosted redirect allowlists, site URLs, provider settings, and email policies are not verified.
  • The mobile sign-in, Keychain storage, refresh flow, and deep-link handling are outside this repository and remain integration work.
  • There is no live Supabase token integration test in CI.
  • Immediate session revocation is not checked against Supabase on each API request.

Official OpenAI documentation confirms that GPT-5.6 Sol supports the Responses API, text input and output, image input, streaming, structured output, and reasoning efforts including low. The application currently uses only text input and complete text output.

Prompt policy

The fixed instruction defines the assistant as a step-by-step voice assistant and requires exactly one practical next step in one short plain-text sentence. Markdown, preambles, and follow-up questions are discouraged except when safety requires clarification.

Data behavior

  • The phone supplies the complete conversation history on each chat request.
  • The backend forwards that supplied transcript to OpenAI.
  • The backend does not write the transcript to its own store.
  • The raw pairing token is hashed before use as the safety identifier.
  • The generated response is stored only in process memory for lens retrieval.

5. Pairing state and data lifecycle

The store is an asynchronous, process-local dictionary protected by one lock. It is sufficient for deterministic v0.1 behavior and unit testing, but it is not a durable or horizontally scalable storage layer.

Pairing record

FieldMeaning
owner_idAuthenticated Supabase user subject that claimed the pairing
stateCurrent lens state
last_phone_activityUTC time used for expiration
response_idRandom UUID-based identifier prefixed with r_
textNewest generated answer only
created_atUTC creation time of newest answer

Expiration and ownership

  • Default time to live is 3,600 seconds.
  • Expired records are removed lazily when another store operation occurs.
  • A new phone request refreshes the activity time.
  • A different user attempting to use an active pairing token receives HTTP 403.
  • An unknown or expired display token receives HTTP 401 and should trigger re-pairing.

Operational consequences

Single-process constraint Restarting or redeploying the service deletes every pairing. Multiple replicas would hold different records, so the phone and lens could observe inconsistent state. Production must run one replica until a shared TTL store is introduced.

The present design also has no durable audit trail, historical conversation store, user profile store, or analytics store. This is intentional for v0.1, but must be reflected in product expectations and deployment settings.

Configuration guardrails

  • APP_ENV must be selected explicitly.
  • Authentication cannot be disabled in dev, trial, or prod.
  • A Supabase URL is mandatory when authentication is required.
  • Supabase URLs must be absolute HTTP or HTTPS URLs.
  • Trial and production require HTTPS.
  • CORS must contain at least one origin.
  • Trial and production reject wildcard CORS.

CORS policy

The application allows GET and POST requests with Authorization and Content-Type headers. Cookie credentials are disabled. Local mode accepts all origins, while hosted environments require explicit origins.

7. Container, GitHub CI/CD, and repository controls

Production container

  • Uses Python 3.12 slim.
  • Copies uv 0.12.9 from the official uv image.
  • Installs the frozen lockfile without development dependencies.
  • Runs under a non-root system user.
  • Exposes port 8000.
  • Checks /healthz every 30 seconds.
  • Starts Uvicorn on 0.0.0.0:8000.
  • Excludes Git data, environments, caches, tests, docs, and Supabase development files from the build context.

GitHub Actions validation

The workflow runs for pull requests into main, pushes to main, and manual dispatch. Older work on the same ref is cancelled through concurrency control.

  1. Check out the repository using a commit-pinned action.
  2. Install Python 3.12.
  3. Install uv 0.12.9 with dependency caching.
  4. Install all locked development dependencies.
  5. Run Ruff.
  6. Run all pytest tests.
  7. Build the production Docker image.

Container publishing

After validation succeeds on main, a dependent job signs in to GitHub Container Registry with the temporary workflow token and publishes:

ghcr.io/adipat2003/metaglasses-backend:latest
ghcr.io/adipat2003/metaglasses-backend:<full-git-commit-sha>

BuildKit layer caching is stored in GitHub Actions. Pulling a private package from a hosting provider will require registry credentials unless package visibility is changed.

Suggested delivery phases

Phase 1: Trial deployment

  • Select a container host and provision exactly one replica.
  • Create and configure the hosted trial Supabase project.
  • Store environment values in the hosting platform.
  • Extend GitHub Actions to deploy the commit-tagged image.
  • Implement mobile authentication and run a complete device-to-lens test.

Phase 2: Operational hardening

  • Add rate limiting, logging, request correlation, metrics, and alerts.
  • Add readiness checks, rollback procedures, integration tests, and vulnerability scans.
  • Define service-level objectives for availability, response latency, and provider failure rates.

Phase 3: Production and scale

  • Create an isolated production Supabase project and production hosting service.
  • Move pairing state into a shared TTL system before adding replicas.
  • Perform load, security, privacy, recovery, and cost reviews.
  • Promote immutable images through trial to production with an approval gate.
